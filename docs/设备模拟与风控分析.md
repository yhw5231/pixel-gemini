# 设备模拟与风控分析（中文）

> 本文分析原项目 `device_simulator.py` / `google_automation.py` 在模拟
> Pixel 10 Pro 设备、登录 Google 账号时存在哪些会被检测、触发风控的
> 问题，并记录本次已修复 / 无法通过代码修复的部分。
>
> **结论先行**：原项目自称"模拟 Pixel 10 Pro 设备"，实际上**只修改了
> User-Agent**，且 UA 内部自相矛盾；浏览器底层指纹、登录流程、出口 IP
> 三个层面的风控信号几乎全部裸露。本次已修复其中可修复的部分，但
> **纯浏览器模拟无法通过 Google 的 Play Integrity / 设备 attestation
> 校验**——这属于无法用代码解决的问题（见文末"无法修复的限制"）。

---

## 一、第二轮深度检查（新增修复项）

第一轮修复（见下）之后继续深挖，又发现并修复了以下检测点：

### 8. sec-ch-ua / Client Hints 版本不一致（重要，已修复）

Chrome 会通过 `sec-ch-ua`、`sec-ch-ua-full-version-list` 等请求头及
`navigator.userAgentData` 主动上报**真实浏览器二进制版本**。原实现：

- UA 声称 `Chrome/137.0.7278.x`，但镜像里的 Debian Chromium 是 v120，
  `sec-ch-ua` 会诚实上报 `Chromium";v="120"` —— **与 UA 交叉对账即可
  拆穿**，比 UA 单独做假更容易触发风控。

修复：
- CDP `Network.setUserAgentOverride` 带 `userAgentMetadata`，让
  `sec-ch-ua` 品牌/完整版本/平台/架构/机型/移动端标志与声称的 UA 完全一致；
- **镜像改用 Google Chrome Stable**（.deb 安装，与 UA 同代 137+），并在
  构建期用 **Selenium Manager** 预缓存匹配的 chromedriver 且做一次无头
  启动冒烟验证，二进制版本与声称版本同代，进一步缩小差异。

### 9. WebGL 软件渲染器泄漏（已修复）

无头 Chrome 的 WebGL 使用 SwiftShader 软件渲染，
`WEBGL_debug_renderer_info` 会暴露类似
`ANGLE (Google, SwiftShader Device …)` 的**数据中心/虚拟 GPU** 特征。
已通过补丁把 `UNMASKED_VENDOR_WEBGL / UNMASKED_RENDERER_WEBGL` 伪造成手机 GPU
（默认 `Imagination Technologies / PowerVR DXT-48-1536` —— 这是 Pixel 10 Pro
Tensor G5 的**真实 GPU**，取自 GSMarena 规格页核验；可用环境变量改）。

### 10. Canvas 指纹全会话相同（已修复）

所有会话共用同一个 Chrome 二进制 → canvas 哈希**完全相同**，多个"新
设备"实为同一指纹集群，可被关联。已注入**按会话种子**的亚像素 alpha
噪声，让每个模拟设备产生独立 canvas 指纹。

### 11. 视口尺寸不真实（已修复）

原 `390×844 @ 3.0` 是 iPhone 比例；Pixel 10 Pro 为 1280×2856 px
@3.0 → CSS 视口约 **427×952**。已改为真实值（可配置）。

### 12. 操作时序机械化（已修复）

原流程固定 `sleep(2)/sleep(2)/sleep(3)`、瞬时输入整段文本——时序特征
可被行为分析识别。已改为随机区间延迟 + 逐字符模拟输入（每字符
20–90ms 随机）。

### 13. 随机值质量与去重（已修复，响应"随机值必须合理、不重复"）

原 `device_simulator.py` 使用 `random`（梅森旋转，可预测序列）且**无去重**
——同一进程内可能生成重复 IMEI / Android ID / UA。修复：

- 全部改为 **`secrets`**（密码学安全随机源）；
- **IMEI / Android ID 进程内注册表去重，永不重复**（IMEI 保持 Luhn 校验
  合法的 15 位、GSMA 风格 TAC 前缀 `35xxxxxx`）；
- Chrome 补丁号池（`137.0.7278.70–150`，真实发布窗口）耗尽前不重复；
  耗尽后允许复用（**真实设备本来就大量共享同一 Chrome 版本**，属合理
  行为），仅告警一次；
- UA / Build fingerprint 随之保持自洽（`user/release-keys`，无 `eng.user`
  矛盾）。

## 二、已发现并已修复的问题（第一轮）

### 1. UA 内部版本自相矛盾（已修复）

| 项 | 原值 | 问题 | 修复后 |
|---|---|---|---|
| 系统 | Android 16（2025 年发布，SDK 36） | — | 不变 |
| Chrome | `124.0.6367.82`（2024 年 4 月） | 2025 年的真机不可能还跑着一年前的 Chrome；相差约 11 个大版本，属"不可能组合" | `137.0.7278.x`（2025 年 9 月，与 Pixel 10 Pro 同期） |
| Build ID | `AP4A.250405.002`（2025-04 补丁） | 与 8 月出厂的 Pixel 10 系统补丁月份不符 | `AP3A.250905.001`（2025-09 补丁） |

`device_simulator.py` 的 `_random_chrome_patch()` 现在只在
`137.0.7278.70–120` 之间随机补丁号，保证同代同系列。

### 2. Build fingerprint 自相矛盾（已修复）

原 `_generate_device_fingerprint()` 生成：

```
google/pixel_10_pro/pixel_10_pro:16/AP4A.250405.002/eng.user.release-keys
```

- `eng`（工程编译版）与 `user`（正式版）、`release-keys`（正式签名）
  同时出现是**不可能的组合**，真实设备上不存在 `eng.user.release-keys`。
- 修复为真实格式：`google/pixel_10_pro/pixel_10_pro:16/AP3A.250905.001/12979047:user/release-keys`。

> 注：该 fingerprint 目前只用于展示记录，并未通过请求头发送（见下文
> "设备身份并未真正落地"）。

### 3. WebView UA 模板（已移除）

原第二个 UA 模板带 `; wv)` 和 `Version/4.0`——这是**嵌入式 WebView**
的标识。用 WebView UA 访问 accounts.google.com 登录会被 Google 的安全
策略直接判定为"不安全浏览器/应用"，反而更容易触发拦截。已删除该模板，
只保留标准 Chrome 移动 UA。

### 4. `as_headers()` 死代码（已修复/清理）

`DeviceProfile.as_headers()` 声称返回 Accept-Language 等请求头，但
**从未被任何代码使用**——实际发出的请求头是 Chrome 默认值，与"设备
语言 en-US"的声明不符。现在浏览器启动参数显式设置 `--lang=en-US`
与设备声明一致。

### 5. 浏览器底层指纹裸露（已修复）

原实现只做了 `excludeSwitches: enable-automation` +
`disable-blink-features=AutomationControlled`，其余自动化痕迹完全裸露。
本次新增 CDP 级反检测脚本（每个新页面加载前注入）：

- `navigator.webdriver` → `undefined`
- `navigator.maxTouchPoints` → 5（修复"手机 UA 但触点数=0"的矛盾）
- `navigator.hardwareConcurrency` / `deviceMemory` → 8 / 8（修复"手机
  设备却暴露服务器 CPU 核心数"的矛盾）
- `navigator.platform` → `Linux armv8l`（ARM 手机平台）
- `navigator.plugins` → 空列表（移动浏览器特征）
- `window.chrome` 对象补齐；删除 `cdc_` 注入标记
- CDP `Emulation.setTimezoneOverride` 把时区固定为 `America/Los_Angeles`
  （可配置），与 UA 语言环境一致

同时移动模拟补上 `"touch": True`，`maxTouchPoints` 不再为 0。

### 6. 登录挑战页处理（已修复）

原 `_gmail_login()` 只处理"邮箱→密码"两步，遇到以下页面直接失败且
**原因不明**：

- 「This browser or app may not be secure」（浏览器不安全警告）
- 人机验证 / CAPTCHA（"Confirm you're not a robot"）
- 二步验证（2FA）、验证码输入页
- 设备确认页、异常流量页（unusual traffic）

修复后：
- 登录结果改为返回**具体失败原因**（如"Google blocked the login
  (challenge page: …)"），Web 界面运行详情页会直接显示；
- 修复了原登录成功判定里的**运算符优先级 bug**：
  `hostname == "myaccount.google.com" or hostname.endswith(".google.com") and "/u/" in path`
  本意为 `A or (B and C)`，现显式加括号；
- 遇到 challenge 页面优先判定为"被风控拦截"而不是误判成功/失败。

### 7. 出口代理支持（已新增）

数据中心 IP（Replit / 云容器）是 Google 风控的**头号红旗**：同一 IP
下频繁登录不同"新设备"，几乎必然触发异常流量拦截。新增可选环境变量
`PROXY_URL`，设置后 Chrome 通过 `--proxy-server` 走代理出口
（建议住宅/移动代理）。

## 三、已识别但**无法通过代码修复**的限制（必须知晓）

以下问题决定了该方案**只能用于自己有合法权限的账号做教育/测试**，
不能保证稳定通过 Google 风控：

| # | 限制 | 说明 |
|---|---|---|
| 1 | **设备身份并未真正落地** | IMEI、Android ID、Build fingerprint 只是内存里的字符串。Selenium 无法把这些注入浏览器，Google 服务端**根本收不到**这些字段。真正的"Pixel 10 Pro"判定依赖 Play Integrity API / 设备 attestation（GMS、硬件签名），纯浏览器 UA 无法伪造 |
| 2 | **Play Integrity / GMS 校验** | 若 offer 兑换链路带 Play Integrity 校验，浏览器环境必然失败 |
| 3 | **2FA / 验证码无法自动通过** | 开启二步验证的账号会在 challenge 页停下，需要人工干预或专门的验证码服务 |
| 4 | **会话不持久** | 每次运行都是全新浏览器会话（无 Cookie 复用），同一账号反复"换新设备"登录 = 账号被盗特征，会加重风控 |
| 5 | **Headless 特征** | `--headless=new`、`--disable-gpu` 等仍可被服务端 JS/行为分析识别，无法彻底消除 |
| 6 | **Canvas/WebGL/字体指纹** | 同一 Chrome 二进制产生的 canvas/WebGL/字体指纹对所有"设备"完全相同——多个账号的底层指纹一致，可被关联聚类 |
| 7 | **IP 与设备区域一致性** | UA 声称美国（en-US/洛杉矶时区）却从数据中心 IP 或错误地区的代理出口，本身即矛盾信号 |
| 8 | **行为特征** | 脚本化操作（点击速度、无鼠标轨迹、页面停留时间）与真人差异明显；Selenium 动作 API 本身可被行为分析识别 |
| 9 | **TLS/JA3 指纹** | 容器内 Chrome 的 TLS 指纹与其声称的 Chrome 版本可能不匹配（HTTP 层主要看 UA，但 TLS 层可交叉验证） |

## 四、降低风控风险的使用建议

1. **只使用自己拥有、无敏感数据的账号**，遵守 Google 服务条款。
2. **配置 `PROXY_URL`**：住宅或移动代理，且代理所在地区与
   `DEVICE_TIMEZONE` / `DEVICE_LANGUAGE` 一致（例如美国西海岸账号用
   洛杉矶时区 + 美国住宅 IP）。
3. **降低频率**：不要对同一账号短时间反复运行；账号之间用不同代理/延迟。
4. **关闭 2FA 的账号**（或准备人工处理验证码）。
5. **先人工浏览器登录一次该账号**（在同一 IP/环境），"养熟"后再自动化，
   可显著降低初始风控概率。
6. **预期失败**：把"登录被拦截"当作正常结果处理——本项目的价值是
   **自动化链路完整可用**，而不是绕过 Google 安全体系。
